<objective>
Close UAT gap 1 (BLOCKER) in the runner and batching decorator: with batch pricing on, relevant waves run live (thread renders and all their attachments), and only non-relevant mail and its attachments go through the Batch API, after the last relevant wave commits (amended D-07, 2026-10-08).

Purpose: one provider batch per relevant wave serialized 24 batch cycles (about 28 min each observed, 24 h SLA) before non-relevant mail started. Relevant threads are a small share of spend; the discount is in non-relevant mail.
Output: runner and decorator change (live waves, Stage B live gate, stale wave batch closing); BatchParityTests, BatchingLlmProviderTests and the 5K batch scale test rewritten for the amended rule.

Out of scope here (plan 07-24, same wave): cost estimate, Ready-card copy, UI-SPEC, media-gating wording. Do NOT touch 07-22-PLAN.md.

Known cosmetic limitation (checker I1, accepted, no change in this plan): wave labels are kept on relevant-wave calls and wave rows stay mapped to batch status, so a wave batch submitted by an earlier build can still show "Batch: d of t done" on its wave row (and a "for wave {i}" activity line) until that batch ends or is closed at run end. Record this under "Known limitations" in the SUMMARY.

Spend note (record verbatim in the SUMMARY under "Known limitations"): closing a stale relevant-wave batch at run end is best effort. The provider may still bill items it completed before the cancel took effect; that spend is not itemized in the journal or RunEnded, because those results are never collected.
</objective>

# Phase 5 — UI Design Contract

> Visual and interaction contract for Phase 5 (Relevant Evidence Generation & Narrative Ledger). Generated by gsd-ui-researcher (`--auto`, no user Q&A), to be verified by gsd-ui-checker.
>
> **Platform:** WinForms desktop (net10.0-windows). All UI is built in code: `InitializeUI()`, a `TableLayoutPanel` root docked `Fill`, row-index comments on every `RowStyle`, and handlers wired only after every control exists.
>
> **Units:** All pixel values are **logical px at 96 DPI**. In code, each one goes through `LogicalToDeviceUnits(n)` on the step, dialog or custom control that owns it. Font sizes are in **points** and come only from `Theme` factories.
>
> **Baseline:** `03-UI-SPEC.md` and `04-UI-SPEC.md` (both approved) are the design system for this phase. Their palette, type scale, spacing tokens, Content x rule, `GridStyle`, `CardPanel`, `StatTile`, `SlimProgressBar`, `ThemedDialog`, state card, banner, status strip, `Plural` helper, tone rules and the DPI & Render Contract (rules 1-16) **apply unchanged** and are not repeated here. This document only adds what Phase 5 needs. Anything not taken from 05-CONTEXT.md, earlier UI-SPECs or the existing code is marked **[DEFAULT]** and listed under Assumptions.
>
> **Quality bar (CONTEXT D-04):** the user runs Windows at 150%. A screen is not done until its 144-DPI render has been inspected against the DPI & Render Contract.
>
> **Sample copy rule:** examples in this document use placeholders (`{name}`, `{PREFIX}-000123`), never names from fictional works.

**Interaction rules**
- **Entering the step** (`OnEnterStepAsync`; pure helper `GenerationUiText.EntryDecision`), first match wins:
  1. A run is active → keep showing it.
  2. No plan, or plan not approved → `Approve the plan first` state card.
  3. A saved run exists whose plan identity differs from the current plan → `Plan changed` state card.
  4. A saved run exists but cannot be read → `Unreadable saved run` state card.
  5. No saved run → `Ready` state card. **Never auto-starts** (generation spends real money; same reasoning as Phase 4 U7 on reopen).
  6. Saved run with unfinished threads → dashboard (tiles, waves, activity rebuilt from the journal) + partial-run banner.
  7. Saved run, every thread written or failed → dashboard with the finished header buttons.
- **Generate Emails / Continue Generating / Retry Failed Threads** all start the same run. It skips threads already journaled as written (including kept-with-warnings) and writes everything else (pending, cancelled and failed). No confirm. [DEFAULT]
- **During a run:** `CanMoveNext` / `CanMoveBack` are false (raise `StateChanged`); header buttons and banner hidden. `Cancel Generation` asks C-G1. Disposing the step cancels the run; `finally` restores state and is a no-op after dispose (WR-07 pattern).
- **Live updates (RUN-07):** progress events from worker tasks are written into a lock-protected snapshot only. A 250 ms `System.Windows.Forms.Timer` on the step applies the snapshot: tiles, the waves grid (in-place cell updates, no row rebuild), new activity rows (inserted in one batch at the top with `SuspendLayout`), the bar and the status text. Workers never touch controls. The shell's existing cost ticker keeps running unchanged. [DEFAULT]
- **Start Over...** asks C-G2. On Yes: delete the EML files the journal lists (only paths under the case folder's `Mailboxes` folder), clear the journal and the ledger, re-project the answer key (all rows back to `Planned`), delete the story-so-far .docx, save, then show the Ready state card.
- **Run end** (finished, cancelled or fatal): merge pending ledger deltas, save the ledger with the case, re-project and write `answer-key.csv` / `answer-key.xlsx` (Status overlay from the journal), write `{folder name} - Story So Far.docx` when the ledger has entries, advance `CaseStage` to `Generation`, save. Leaving the step retries any of these writes that failed.
- **Next gate** (`ValidateStepAsync`): run active → Next disabled. Otherwise always advance to Case Summary (a partial corpus is a valid result; no prompt) [DEFAULT].
- `< Back` returns to Review Plan (enabled whenever no run is active).
- Keyboard: Tab order follows header buttons → banner button → Waves grid → Activity grid → `Cancel Generation`. Tiles are not tab stops.

### S5. Generated email look (the EML content contract, D-16..D-21)

Not app chrome, but it is what the user sees in a mail client, so it is fixed here.

- **Format:** `multipart/alternative`, plain-text part first, HTML part second. HTML comes from `HtmlEmailFormatter.ConvertToHtml(plainText, OrganizationTheme)` (plan-based overload allowed). The body markup the model may use is limited to: `**bold**` (at most 2 runs per message), bullet lists (`- ` lines, at most 6 items, at most 1 list per message), and at most one simple table of figures (at most 4 columns x 6 rows, pipe syntax) per thread. No headings, colors, links or images from the model. Code strips anything else. [DEFAULT: "not too crazy"]
- **Organization theme:** each `CaseOrganization` domain gets a deterministic `OrganizationTheme`: one of 8 fixed palettes chosen by a stable hash of the domain (stable across runs and machines, no LLM call), fonts from the existing `ThemeGenerator` allowlist, colors through its hex sanitizer. Personal and unknown domains use `OrganizationTheme.Default`. [DEFAULT]
- **Signature:** code appends the cast `Signature` verbatim after the body, separated by one blank line. Short replies may use the first name or initials only when `SignatureStyle` allows. The model never writes a signature.
- **Quoted history:** code builds it from earlier rendered messages (reply: `On {ddd, MMM d, yyyy} at {h:mm tt}, {Name} <{address}> wrote:` + quoted text; forward: the standard `---------- Forwarded message ----------` block with From/Date/Subject/To). Subjects get `RE: ` / `FW: ` via `ThreadingHelper`, never doubled.
- **Privileged markers (D-18):** decided per thread by code. About 85% of privileged threads are labeled: the first line of every message body is the bold banner `PRIVILEGED & CONFIDENTIAL - ATTORNEY-CLIENT COMMUNICATION`, and about 40% of labeled threads also prefix the subject with `Privileged & Confidential - `. The remaining ~15% carry no label. Counsel's cast signature is appended like any other.
- **Headers:** `X-ReelDiscovery-DocID: {PREFIX}-000123` on every copy; Message-ID domain = the sender's organization domain; `In-Reply-To` / `References` chains per thread. Sender's copy in `Mailboxes/{custodian}/Sent Items`, recipients' copies in `Mailboxes/{custodian}/Inbox` (Phase 4 planned paths).

### S6. "Story so far" .docx layout (CORP-11, D-10)

Built with the existing Word builder used by `CaseGuideDocxExporter`, file `{folder name} - Story So Far.docx` in the case folder.
- Title: `{Case title} - Story So Far` (Heading 1). Line under it: `Internal narrative ledger written by ReelDiscovery from {Plural(t, "generated thread")}, {MMM d, yyyy} to {MMM d, yyyy}. Not part of the produced corpus.`
- Grouped **by month** (Heading 2 `March 2024`), entries in date order. Each entry is one paragraph: bold lead `{MMM d, yyyy} · {Kind}` (Commitment, Figure, Meeting, Decision, Person, Document, Other), then the statement; if a value exists, ` ({value})`. A second, smaller line: `Known to {names, comma-separated} · Facts {F-012, F-013} · Issues {I-03} · Source {DocID}` (empty clauses dropped).
- A final section `Threads kept with warnings` lists thread ID, subject and the violations, when any exist. [DEFAULT]

# Stack Research

**Domain:** AI-driven synthetic eDiscovery corpus generator (brownfield .NET WinForms desktop app; adding multi-provider LLM, batch, structured output, caching, legal .docx, answer key, local persistence)
**Researched:** 2026-09-29
**Confidence:** HIGH for package versions/API surfaces (verified against NuGet and SDK source), MEDIUM for architecture choices built on them

> Scope: only the additions for this milestone. The existing stack (WinForms, OpenAI 2.1.0, MimeKit 4.18.1, DocumentFormat.OpenXml 3.0.2, System.Text.Json) is covered in `.planning/codebase/STACK.md`.

## Headline Findings (read first)

1. **The official Anthropic C# SDK is the `Anthropic` NuGet package (v10+; currently 12.51.0, published 2026-09-22).** It is generated by Anthropic, targets netstandard2.0/net8.0/net9.0, and covers Message Batches (`client.Messages.Batches.*`), structured outputs (`OutputConfig` + `JsonOutputFormat`, plus a typed `Create<T>()` helper), prompt caching (`CacheControlEphemeral` with `Ttl`, both per-block and top-level automatic), and exposes an `IChatClient` via `AsIChatClient()`. Package versions 3.x and below were the tryAGI community SDK, which has moved to `tryAGI.Anthropic`. **Do not use the old community SDKs.** (HIGH)
2. **.NET 8 goes out of support on 2026-11-10, about six weeks from now.** .NET 10 is the current LTS (supported until 2028-11-14). Retarget to `net10.0-windows` early in the milestone. It's a one-line change for WinForms, and every package below supports net8.0 anyway, so nothing blocks it. (HIGH)
3. **`dall-e-3` was shut down on 2026-05-12.** The existing `OpenAIService` hard-codes it, so the image feature is probably broken in production today. The replacements are `gpt-image-1`, `gpt-image-1-mini` and `gpt-image-2`. These return base64 bytes rather than URLs. Fix this when upgrading the OpenAI SDK. `tts-1` is not deprecated. (HIGH for the shutdown, MEDIUM for the replacement IDs)
4. **Upgrade `OpenAI` 2.1.0 to 2.14.0.** You need it for current models, typed usage details (cached tokens) and a current `BatchClient`. `Microsoft.Extensions.AI.OpenAI` 10.10.x also *requires* OpenAI 2.14.0 if you use it. In the .NET SDK, `BatchClient` and `ResponsesClient` are still `[Experimental("OPENAI001")]`. `ChatClient` and `ChatResponseFormat` are GA. (HIGH)
5. **Batch and prompt caching stack on both providers (both give 50% off batch).** Anthropic warns that batch cache hits are best-effort (30–98%). It recommends the **1-hour cache TTL** for batches that share context, because batches often take longer than 5 minutes. (HIGH)

## Provider Abstraction: Recommended Shape

**Recommendation: build a thin, app-owned `ILlmProvider` on top of the two native SDKs. Use Microsoft.Extensions.AI only for schema generation. Do not make `IChatClient` the core abstraction.** (MEDIUM, design judgment backed by the verified API surfaces)

Why:
- **Batch is the deciding factor.** `IChatClient` has no batch concept. Both batch APIs take *native* request bodies: Anthropic's `BatchCreateParams.Requests[].Params` is a `MessageCreateParams`, and OpenAI's batch is a JSONL file of `/v1/chat/completions` bodies. If sync calls go through `IChatClient` but batch calls are built natively, you get two translators that will drift. Prompts, cache breakpoints and schemas will differ between sync and batch, which breaks cache hits and gives you inconsistent output.
- **One translator per provider** (`LlmRequest` → `MessageCreateParams` / chat-completion JSON) used for both sync and batch keeps them byte-identical. That lets you retry a failed batch item synchronously with exactly the same request, and keeps cache prefixes identical across sync and batch.
- Cache control is where the two providers differ most. Anthropic needs explicit `cache_control` breakpoints plus a TTL. OpenAI caches automatically for prefixes ≥1024 tokens, and `prompt_cache_key` only helps routing. Your own abstraction can express this as "stable prefix blocks" plus "variable suffix" and let each translator map it natively.
- Both SDKs *do* ship first-party `IChatClient` adapters. `Anthropic.AsIChatClient()` maps `ChatOptions.ResponseFormat` to `output_config.format`, maps `AIContent.WithCacheControl` to `cache_control`, and reports `CachedInputTokenCount`. So if you want `IChatClient` later (for middleware or telemetry), it can wrap the same clients. You lose nothing by starting native.

Suggested contract (illustrative):

```csharp
public interface ILlmProvider
{
    string Name { get; }                                   // "anthropic" | "openai"
    Task<LlmResult<T>> GenerateAsync<T>(LlmRequest req, CancellationToken ct);
    Task<string> SubmitBatchAsync(IReadOnlyList<LlmBatchItem> items, CancellationToken ct); // returns provider batch id
    Task<BatchStatus> GetBatchStatusAsync(string batchId, CancellationToken ct);
    IAsyncEnumerable<LlmBatchItemResult> ReadBatchResultsAsync(string batchId, CancellationToken ct);
}
// LlmRequest = { Model, StablePrefix (case guide, cast, timeline), VariableSuffix (this thread's brief),
//                JsonSchema (from AIJsonUtilities), MaxTokens, CacheTtl }
```

## Feature-by-Feature Stack Notes

### Structured outputs (both providers)
- **Anthropic:** `OutputConfig = new() { Format = new JsonOutputFormat { Schema = ... } }`. This is GA on Opus 4.5+/Sonnet 4.5+/Haiku 4.5/5.x models. Every object must have `additionalProperties: false`. **Not supported:** recursive schemas, `minimum/maximum`, `minLength/maxLength`, `pattern`, and `minItems` > 1. The first request for each schema pays a grammar-compile latency, and the compiled grammar is cached for 24h. Changing the schema invalidates the prompt cache for that prefix. The SDK also has `client.Messages.Create<T>()` and `StructuredOutput.ToJsonOutputFormat<T>()`, which use its own schema inference. Prefer one shared schema source (below) so both providers get the same schema. (HIGH)
- **OpenAI:** `ChatResponseFormat.CreateJsonSchemaFormat(name, BinaryData.FromString(schema), jsonSchemaIsStrict: true)`. Strict mode requires every property to be in `required` (use nullable types for optional fields) and `additionalProperties: false`. (HIGH)
- **Shared schema source:** `AIJsonUtilities.CreateJsonSchema(typeof(ThreadDto), serializerOptions: ..., transformOptions: new() { DisallowAdditionalProperties = true, RequireAllProperties = true })`. Keep DTOs free of `[Range]`/`[StringLength]`/`[RegularExpression]`, because Anthropic rejects those constraint keywords. Cache the schema string per DTO type so the bytes are identical on every call (this protects both the grammar cache and the prompt cache). (MEDIUM, API verified, cross-provider acceptance needs a smoke test)
- Structured output works inside batch requests on both providers, because the batch body is just the normal request body. (MEDIUM, implied by docs but not stated explicitly for either)

### Batch APIs
| | Anthropic Message Batches | OpenAI Batch |
|---|---|---|
| .NET API | `client.Messages.Batches.Create(new BatchCreateParams { Requests = [ new() { CustomID, Params = MessageCreateParams } ] })`, `Retrieve(id)` → `ProcessingStatus == "ended"`, `ResultsStreaming(id)` → `IAsyncEnumerable<MessageBatchIndividualResponse>` (succeeded/errored/canceled/expired) | Build JSONL (`custom_id`, `method`, `url: /v1/chat/completions`, `body`), upload via `OpenAIFileClient.UploadFileAsync(..., FileUploadPurpose.Batch)`, `BatchClient.CreateBatchAsync(BinaryContent, waitUntilCompleted:false)` (protocol-level, `OPENAI001`), poll `GetBatchAsync`, download `output_file_id` + `error_file_id` |
| Limits | 100,000 requests or 256 MB per batch. Most finish in under 1h, expire at 24h. Results kept 29 days. | 50,000 requests or 200 MB per file. 24h window. Output files deleted after 30 days. |
| Discount | 50% on all usage, stacks with caching | 50% |
| Unsupported in batch | `stream`, fast-mode `speed`, `max_tokens: 0` (cache pre-warm) | — |
| Confidence | HIGH | HIGH (limits), MEDIUM (exact .NET call sequence, because it's protocol-level and experimental) |

At 5K emails the corpus fits in a single batch on either provider. Split it anyway: one batch per generation wave (for example, relevant threads grouped by timeline phase) so a bad wave can be retried on its own. **Persist `batchId` + `custom_id → thread` mapping in SQLite before polling.** Batches outlive the app process, and losing the ID means paying for results you can't retrieve.

### Prompt caching (large shared case-guide context)
- **Anthropic:** Put the case guide (core doc, cast, key-facts timeline, style rules) as `System` text blocks with `CacheControl = new CacheControlEphemeral { Ttl = "1h" }` on the last stable block. Put per-thread instructions *after* the breakpoint. There are up to 4 breakpoints and a 20-block lookback. The minimum cacheable prefix is 512 tokens on 5.x models, 1,024 on Sonnet 4.5/4.6, and 4,096 on Haiku 4.5 / Opus 4.5–4.6. Pricing: 5m writes are 1.25x, 1h writes 2x, reads 0.1x (0.05x on Opus 5.5). **A cache entry only exists after the first response starts,** so fire one request, wait for its first response, then fan out in parallel. Otherwise N parallel requests each pay the write cost. Verify with `usage.CacheReadInputTokens > 0`. (HIGH)
- **OpenAI:** Caching is automatic for prefixes ≥1024 tokens, at a 0.1x read price on most models. Set `prompt_cache_key` (for example, the case ID) to improve routing. The typed `PromptCacheKey` / `PromptCacheRetentionPolicy` (`InMemory` / `Max24Hours`) exist only on the **experimental** `ResponsesClient` options in SDK 2.14. `ChatCompletionOptions` has no typed property. On chat completions, either rely on automatic caching or patch the JSON body. Newer GPT-5.6+ models add explicit breakpoints and a 1.25x write cost, but the docs describe these only for the Responses API. (MEDIUM, docs are model-generation-specific and shifting)
- **Design consequence:** the case-guide prefix must be **byte-stable**. Serialize it once per run (fixed ordering, no timestamps or GUIDs, no per-call randomness) and store the rendered text in SQLite. Every sync and batch request uses exactly that string.

### Legal .docx (complaints, depositions with line numbers)
- Use raw `DocumentFormat.OpenXml` 3.5.1 plus a new `LegalDocumentBuilder`. Model it on the existing `OfficeDocumentService`, as its own service rather than inside `EmailGenerator`.
- **Deposition transcript:** `SectionProperties` with `LineNumberType { CountBy = 1, Restart = LineNumberRestartValues.NewPage, Distance = ... }`, exact line spacing (`SpacingBetweenLines { LineRule = Exact }`) sized so 25 lines fill the page, and a monospaced font (Courier New 12pt is the reporter convention). Include a caption page, appearances, the Q/A body and a reporter certificate.
- **Complaint/pleading:** caption table, numbered paragraphs via a `NumberingDefinitionsPart` (one abstract numbering, restarting per count), headings per cause of action, and a signature block. Pleading-paper left-margin numbers 1–28 (a California style) can use the same `LineNumberType` mechanism. Real pleading paper uses a header-anchored text box, but that isn't worth it for v1. (MEDIUM, the approach is standard Word features, but verify the rendering in Word)
- Generate the long documents **section by section** (caption, parties, facts, each count, prayer) with structured output per section. Assemble them in code. That way no single LLM call has to produce 15–30 pages, and each section can cite key-fact IDs.

### Local persistence
- **SQLite project database** (`<output>\<case>\case.db`) with tables for `case_guide`, `characters`, `key_facts`, `plan_items` (planned threads/emails with status), `batch_jobs`, `batch_items`, `documents` (written file path, custodian, date, relevance, issue/fact links). Commit after each thread is written to disk.
- **JSON sidecar exports** (`case-guide.json`) for human-readable, diffable case-guide snapshots. You get them almost for free with System.Text.Json.
- Use WAL mode (`PRAGMA journal_mode=WAL`) so the UI thread can read progress while workers write. Use one connection per worker, or serialize writes through a single writer, because SQLite has a single writer.

| Assistants API / `AssistantClient` | OpenAI shut down the Assistants API on 2026-08-26 | Chat Completions or Responses |

## Stack Patterns by Variant

**If generating relevant (story-bearing) threads interactively while the user watches:**
- Use sync calls on a strong model (Claude Sonnet 5.5 / Opus 5.5, or an OpenAI flagship) with a cached case-guide prefix, pre-warm the cache, then fan out.
- Because latency matters and the user may cancel or adjust.

**If generating bulk non-relevant filler (newsletters, daily business, decoys), which is most of the 5K:**
- Use the Batch API on a cheap model (Claude Haiku 4.5 at $0.50/$2.50 per MTok batch, or a cheap OpenAI tier) with a 1h-TTL cached prefix.
- Because the cost drops by 50% or more, and the 1–24h latency is acceptable for filler.

**If a batch item errors or expires:**
- Resubmit that single `custom_id` synchronously with the *identical* request built by the same translator.
- Because one failed item must not abort the run (a stated requirement), and the identical request keeps cache and prompt parity.

- **Anthropic (HIGH, from official batch/caching docs):** Opus 5.5 $4/$20 per MTok standard ($2/$10 batch), Sonnet 5.5 $2/$10 ($1/$5 batch), Haiku 4.5 $1/$5 ($0.50/$2.50 batch). SDK constants include `Model.ClaudeOpus5_5`.

### Detailed Findings

#### W1 (WARNING): Generate Corpus never re-checks guide staleness; approval survives guide edits until Review Plan is visited

- **From/To:** Phase 3 guide edits → Phase 4 approval → Phase 5/6 generation.
- **Evidence:** `CorpusApproval.WithdrawApprovalIfStale` is called only in `StepReviewPlan.Run.cs:113`. `StepGenerateCorpus.Run.cs` gates only on `Corpus.Approved` (lines 142 and 390), and nothing under `Services/Evidence` or the generate step checks `IsGuideStale` or a guide hash. Two normal paths skip Review Plan:
  1. Case Summary **Generate Emails** (`StepCaseSummary.cs:554`, shown while nothing has been generated) jumps straight to Generate Corpus. The plan row warns that the plan is stale, but the button still works.
  2. Reopening a case at `Stage >= Generation` opens Generate Corpus or Case Summary directly, after the user went Back, edited the guide and closed.
- **Effect:** the run renders the old plan against the edited guide. A deleted character renders as its raw ID with an empty address (`PeopleDirectory.NameOf`/`EmailOf`) and lands in the `Unassigned` mailbox (`PlanNumbering.cs:104`). A renamed custodian changes `CustodianFolders` partway through the corpus, so one mailbox splits across two folders. The Case Guide step shows no warning that an approved plan or a generated corpus depends on it.
- **Fix:** show a stale-guide state card in `GenerationUiText.EntryDecision` (or call `WithdrawApprovalIfStale` on Generate Corpus entry and before `RunCoreAsync`), and hide or gate Generate Emails when `PlanRowStale` is true.
- **REQ-IDs:** GUIDE-09, PLAN-06, PLAN-07, CORP-01, CORP-02, OUT-01, KEY-03.

#### W2 (WARNING): Discovery Documents cannot be reached without an approved corpus plan, contrary to 08-CONTEXT D-07

- **Evidence:** D-07 says "every corpus step can already be passed with Next, so the step is also reachable without a corpus." But the Next gate on Review Plan returns `NoPlan` ("There is no corpus plan yet. Click Plan Corpus, then approve the plan.") and blocks (`CorpusUiText.PlanNextGate`, `StepReviewPlan.Run.cs:153-160`). Entering Review Plan auto-plans, which is a paid LLM run. Case Summary is the only other way in (`NavigateToStep(typeof(StepDiscoveryDocuments))`), and it sits after Review Plan as well. `CaseStage` has no Discovery value (D-09).
- **Effect:** a user who wants only the pleading, guide and discovery set must pay for corpus planning and approve it, which also writes the answer key and protocol. Generating emails is not required, so the corpus-optional path works only from "plan approved, nothing generated".
- **Fix:** let Next on Review Plan skip ahead with a confirm when there is no plan, or add a "Discovery Documents" link on Case Guide or Review Plan.
- **REQ-IDs:** ANC-01, ANC-02, ANC-03, ANC-04, ANC-05.

#### W3 (WARNING): Corpus changes that keep the PlanId do not mark discovery documents stale

- **Evidence:** `DiscoveryStaleness.Check` compares only the guide, core and caption hashes and `CorpusPlanId`. Start Over (`GenerationReset`) and Regenerate Thread (`ThreadInvalidation`) keep the PlanId, delete EMLs and never touch the Discovery folder.
- **Effect:** after Start Over, depositions and genuineness RFAs cite exhibit DocIDs (`DepositionPlanner.cs:725-727`) whose EMLs no longer exist. They exist again only after a full regeneration, and then with different text. The documents still show as current.
- **REQ-IDs:** ANC-05 (and ANC-01, ANC-03 for exhibits and genuineness RFAs).

#### W4 (WARNING): A manual relabel in the answer key is silently overwritten

- **Evidence:** QA-01 relabeling is "edit the answer key spreadsheet" (`QaUiText.cs:296`). Every later writer rebuilds the key from the plan and journal and replaces the file atomically: each run checkpoint (`GenerationRunner.cs:1041`), reopen crash recovery (`StepGenerateCorpus.Run.cs:1151`), the key retry on leaving the step (`:1044`), Regenerate Thread (`ThreadInvalidation.cs:98`) and Start Over (`:929`). No copy warns about this, and no relabel overlay is persisted.
- **REQ-IDs:** QA-01, KEY-03.

#### W5 (WARNING): Switching the text provider strands pending batches of the other provider

- **Evidence:** `BatchingLlmProvider.Recover` resumes only `r.Provider == _transport.Kind` (`BatchingLlmProvider.cs:217`, by design). `BatchLedger.PendingBatchCount` counts every provider (`BatchLedger.cs:274-280`), and its count drives the banner and close-prompt clauses.
- **Effect:** suppose a user goes Back to API Configuration mid-case and switches provider. Items still in the old provider batch are submitted again under the new provider, so they are paid twice. The old batch is never collected or billed in the app unless the user switches back, and the "N batches pending" banner stays up.
- **REQ-IDs:** RUN-03, RUN-04, PROV-01, PROV-07.

#### W6 (WARNING): After Regenerate Thread or a partial run, Case Summary gives no direct way to Continue Generating

- **Evidence:** the Generate Emails button on the Mailboxes row shows only while nothing has been generated (`GenerationUiText.cs:965`, `ShowSecondary = !input.Generated`). The C-Q1 copy says "Go to Generate Corpus and click Continue Generating" (`QaUiText.cs:313`). A case reopened at Stage=Summary lands on Case Summary, so the user must click Back twice, through Discovery Documents.
- **Effect:** the flow still works, but the copy points to a step with no link to it.
- **REQ-IDs:** QA-01, QA-03, RUN-06.

#### W7 (WARNING): Planning traceability is out of date with the verified code

- **Evidence:** `.planning/REQUIREMENTS.md` still shows NOISE-01..05 and ATT-01..04 as `[ ]` and "Pending", and RUN-02 and OUT-01 as "Partial (... in Phase 6)". The code wires them: `NonRelevantSkeletonBuilder` → `FillerRenderer`/`RenderProfile` → `MailboxWriter`, and `AttachmentUnitOfWork` → `OfficeDocumentService`/`CalendarService`/`IMediaGenerator`. 06-VERIFICATION is `passed`, 6/6. `.planning/ROADMAP.md` line 15 also leaves Phase 1 unchecked.
- **REQ-IDs:** NOISE-01..05, ATT-01..04, RUN-02, OUT-01.

#### W8 (WARNING, low): Dead legacy type survives the cutover

- **Evidence:** `Models/Attachment.cs` `class Attachment` (legacy byte-payload model) and `enum AttachmentComplexity` have no references. Only `enum AttachmentType` is used. The deleted-type guards in `PlatformTests` do not cover this type.
- **REQ-IDs:** PLAT-05.
